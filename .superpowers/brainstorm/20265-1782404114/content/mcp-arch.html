🎯 为什么用 MCP 而不是直接 API？

✅ MCP 优势
  • 利用 IDE Agent 的原生搜索能力 — 无需自建爬虫
  • Agent 自动多步推理 — 搜索→规划→验证→调整
  • 用户零配置 — 安装 MCP Server 即可，无需 Key
  • Agent 的上下文记忆 — 对话历史自动保留
  • Agent 的代码执行能力 — 可运行脚本、处理数据
  • 一个 MCP Server，多 IDE 通用 — Kimi Code、Codex、Claude Code、Cline...
⚠️ MCP 局限
  • 用户必须在IDE 环境中使用 — 不适合普通用户
  • Agent 行为不可完全控制 — 依赖厂商实现
  • 响应延迟较高 — Agent 思考 + 多步工具调用
  • IDE 外（手机/网页）无法使用 MCP
  • 需要用户安装配置 MCP Server

🏗️ 双轨架构：MCP for IDE + API for Web/App

🎯 核心洞察：MCP 和 Web API 不是互斥的
MCP Server 和 Web API 可以共享同一套后端逻辑。MCP 是 IDE Agent 的"入口"，Web API 是浏览器/手机的"入口"。
🖥️ IDE 用户（MCP）
• 安装 Periplus MCP Server
• 在 Kimi Code / Codex 中对话
• Agent 自动调用工具规划旅行
• 结果在 IDE 中展示（或打开浏览器）
• 适合：开发者、高级用户
🌐 Web/App 用户（API）
• 打开 Periplus 网页/小程序
• 表单/对话输入需求
• 后端调用 AI API（BYOA 或平台 Key）
• 结果在地图/UI 中可视化
• 适合：普通用户、移动端
🔄 共享层：同一套业务逻辑、同一套数据库、同一套高德 API 调用

🤔 关键决策：MCP 的优先级

A

MCP 优先

先实现 MCP Server，让 IDE 用户先用起来。验证 Agent-Native 交互后，再扩展 Web 端。开发量最小，最快验证。

B

Web 优先

先完善 Web 端（地图可视化是核心），MCP 作为后续扩展。用户基数更大，但 AI 交互验证较慢。

C

并行推进

共享后端逻辑，同时实现 MCP Server 和 Web API。开发量最大，但两条线互不阻塞。
