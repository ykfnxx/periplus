# 从用户原话到完整行程

这个套件以用户任务为入口，补齐接口回归无法回答的“到底能不能帮我规划好”。[user-scenarios.json](user-scenarios.json) 收录 **16 个单点理解场景 + 12 个全程场景**；每个全程场景提供 3 种等义口语表达，共 36 个初始表达。它们与原有 31 个技术场景合计 59 个逻辑场景。口语变体不是新的独立任务，汇总时不能给同一任务三倍权重。

## 主案例 E01：杭州三日游，不去灵隐寺

初始状态：普通账号已经拥有一个空旅程；正式事件为 0，基准修订记为 R0（实际数值不要求为零）。工具使用合成地点响应，模型真实运行；成功提案不得预置数据库。

| 阶段 | 用户或环境动作 | 必须观察到的结果 |
| --- | --- | --- |
| 首句 | “给我规划一个杭州三日游，不去灵隐寺” | 理解城市=杭州、时长=3天、排除=灵隐寺。缺绝对日期先询问；不能拿系统当天填充可应用日期。 |
| 澄清 | “2026年11月15日开始，玩到17日。” | 目标日期确定为15/16/17日，排除要求继续有效。 |
| 补充要求 | “每天10点后开始，一天最多两个景点；午饭都要有。具体店名不用存，保留文字安排就行。” | 生成包含三天活动及午餐的 v1；每日最多2个景点，活动不早于10点，不把即时供应商门店/坐标写入预览保存值。 |
| 第一次调整 | “第二天别太满，午饭定在11点半，灵隐寺仍然别排。” | v2 的第二天午餐为11:30；其余明确约束保留，不能为调整一天重建全部事件。 |
| 第二次调整 | “第三天16点要到杭州东站，交通时间没查清楚就标出来，别说保证来得及。” | 最终版有17日16:00车站安排，未核实交通可行性明确展示；未擅自声明已验证。若该要求无法在当前安排下满足，先澄清而不是冒充成功。 |
| 检查预览 | GET、页面差异与数据库快照对照 | 覆盖3天，无灵隐寺活动；所有已明确约束可逐条核对；正式事件仍为0。展示文字含“不去灵隐寺”本身不是违规。 |
| 确认 | 测试用户确认当前显示版本，再发送 apply | 仅一次修订，实际保存与预览一致；应用期间模型与地点工具调用数为0。 |
| 重开 | 关闭页面后重新进入旅程，重新 GET | 从数据库恢复同一事件顺序、日期和业务字段；不依赖内存中的提案列表冒充保存成功。 |

不规定唯一景点清单。满足约束的西湖/博物馆/城市漫步等方案均可；不能为了便于评分强迫输出某条“标准答案”。是否确实慢节奏、地理上是否绕路是独立质量项，不能拿“模型说轻松”当作已经满足。固定地点夹具可以提供人工定义的区域标签判断跨区往返；真实交通耗时只能用有证据的路线数据判断。

## 单点用例覆盖

| 能力 | 用例 | 典型输入 |
| --- | --- | --- |
| 缺字段与否定 | S01–S04 | “杭州玩三天，灵隐寺就别排了”；“别把西湖删了，灵隐寺才是不去的那个”；“改成两天” |
| 偏好与显式约束 | S05–S06 | “别太赶”；“每天10点之前别给我排活动” |
| 指代与局部编辑 | S07–S10 | “第二天那个馆”；“午饭不是12点，是11点半”；“时间改回去，取消景点照旧” |
| 语义与行动边界 | S11–S12 | “不是不去西湖”；“查一下，别替我订” |
| 复合要求与冲突 | S13–S16 | 提前午餐并删下午茶；晚到站却要求更早出发；排除某馆区；含住宿的两人总预算 |

单点场景只检查这一轮输出是否选择了正确动作并保留前置约束；需要澄清的场景以有效 question 为正确结果。不强迫所有单点都产生可应用版。涉及删除/移动时观察服务预演，不仅看模型文字答复。

## 可重复的用户和环境驱动

`utteranceVariants` 每次只选一条开始，三个变体分别建独立旅程。`answerBank` 是用户可公开提供的信息，不是隐藏评分答案：日期缺失时等待系统提问再回答；pace/scope 等必要补充要求在日期澄清后主动发送，即使系统没问也要发送。所有 oracle 依赖的具体要求必须实际进入本次对话，不能用未发送的用户偏好扣分。选择类答复只能对当前展示候选作出；不注入夹具内部 POI ID。

`followupUserTurns` 按顺序在前一份预览完成后发送；cancel-turn 的第二条在新运行已启动、尚未结束时发送。环境通过受控工具延迟形成取消窗口。expire-choice 在问题产生后跨过120秒并重开；concurrent-edit 在预览后用第二个正常账号提交修改；lost-apply-response 在服务确认提交后丢掉响应。故障不是在任意睡眠后碰运气注入。

每个全程场景最多10次用户输入（首句、补充、答复和调整均计数）；用户点击应用/取消/重试等另记操作数。达到上限仍未到预期终点为失败，重复追问不能靠无限轮次洗成成功。没有预定义答复的问题记 needs_review，由人工检查是合理澄清还是题目遗漏，修订用例前不能偷偷补答案。UI取消/放弃必须显式触发对应操作，不把自然语言生成结果当作已经调用取消接口。

## 夹具具体化要求

实现 runner 时按场景实例化以下最小数据，不使用真实用户数据：

- `dated-hangzhou`：已知日期2026-11-15起三天；`hangzhou-three-day-preview` 有三天已发布预览。
- `hangzhou-with-westlake-and-lingyin`：两个不同ID活动西湖、灵隐寺，日期固定；用于否定作用域。
- `preview-two-museums-day2`：第二天有两个不同馆；`preview-one-museum-day2` 只有一个，形成最小对照实验。
- `preview-day2-lunch-12-tea-15`：第二天12:00午餐、15:00下午茶；`dated-xiamen-two-day` 为11月15–16日，其他活动带不可丢失备注。
- `R12-two-turn-preview`：R12的取消景点/新增直达交通，以及午餐12:00改11:30两轮预览。
- 地点夹具除名称、城市、馆区、坐标，还给评分端维护语义ID/别名/区域标签；这些评分标签不发给模型。禁止景点判定基于实际活动目标及引用，而非整段回复字符串匹配。若文字方案无法自动确定，交盲评，不能直接算通过。

合成地点数据仅用于可重复行为判断，不证明真实营业时间、价格、交通或地图数据正确。地理合理性和实际工具连接在 live 层另报。
