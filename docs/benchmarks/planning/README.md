# Pi 旅行规划 workflow benchmark 设计

## 基准与交付范围

本设计基于 PR #70 的 `7c3fd2ab2d10e9b62848b6f671a663bfba0331c9`，分支 `feat/agent-plan`。规范来源是 `docs/superpowers/specs/2026-11-11-pi-planning-workflow-spec.md`（原稿位于项目主工作区；[共享 SPEC](https://app.raft.build/artifacts/5niAJkQrtr54F2Dq7UgBZU)）；本设计包含59个逻辑场景：19个工作流不变量、10个工具/模型诊断、2个真实服务场景，以及16个单点口语理解和12个全程旅行任务。全程任务各有3种等义表达，共36个初始表达。`cases.json` 与 `user-scenarios.json` 是设计用例目录，不是已经实现的 runner。本提交不改产品代码，也不宣称真实模型已跑通。

主问题是：**用户随口提出旅行要求后，能否经过澄清、规划、调整、确认，得到正确保存的完整行程？** 工作流不变量和工具诊断为这个目标提供分项解释。

先阅读 [用户全程案例](user-workflows.md)，其中完整展开“给我规划一个杭州三日游，不去灵隐寺”；口语及具体行程输入在 [user-scenarios.json](user-scenarios.json)，判分与实验规模在 [metrics.md](metrics.md)。不把脚本输出生成的成功预览计作模型能力，不将单元测试数量当作端到端成功率。

## 三个执行层

| 层 | 被测对象 | 输入与依赖 | 结论范围 |
| --- | --- | --- | --- |
| workflow | 六个接口、服务、数据库事务、恢复及确认 | 固定 `PlanningRuntime` 输出、独立 PostgreSQL、真实普通用户会话；明确注入故障 | 状态机、权限、持久化和恢复正确性，不评价模型 |
| model | Pi 完整工具循环到可提交预览 | 真实模型 + 人工合成的固定 MCP 搜索/周边/详情响应；沿用真实适配器解析 | 模型编排、澄清、工具选择、引用及留存行为，可重复比较 |
| live | 实际模型 + 实际高德 MCP | 项目获准使用的 Key、杭州和成都实际查询 | 外部连接与真实服务能力；不与固定数据成绩混合 |

workflow 的 HTTP 检查不可仅在数据库预置一个成功版本再宣称“生成成功”。需要驱动真实 run 生命周期：测试服务在装配点接固定 runtime，再经 HTTP 创建/读取/答复/应用。当前 HTTP 入口直接装配生产 runtime，后续 runner 如需注入，只在测试启动装配中完成，不添加面向用户的测试开关或测试路由。服务层固定 runtime 可先复用现有 `executePlanningRun` 参数。

model 层通过 `createPiPlanningRuntime` 的现有依赖边界提供固定 MCP 连接，真实模型 stream 保持默认；以 `AmapPlaces` 实际解析结果，不能直接给出期望 `finish_turn`。live 层不替换任何外部响应。三层均使用独立测试账号和数据库，不接开发机正式旅程。

## 固定数据与用户脚本

基准时钟：`2026-11-14T00:00:00Z`，时区 `Asia/Shanghai`。完整日期在澄清答复中固定；首句保留真实口语中的缺日期、相对时间和歧义，不能在评分前替用户补齐。模型未获得明确日期时不能单凭测试时钟猜出发日。初始状态、用户原话和故障安排属于 runner 输入；期望命令/评分条件不进入模型上下文。

- **R12 杭州旅程**：唯一顺序 `L → T1 → G → T2 → S`。L 为 2026-11-15 12:00 湖滨午餐，含两张合成照片及正文；G 为景点；S 为杭州东站，备注“车站备注保留”；T1 连接 L/G，T2 连接 G/S。事件 ID 固定为逻辑别名，落库时按本次 run 映射唯一真实 ID。记录初始投影、照片/账单关联、酒店和路线业务值及修订数。
- **空旅程**：已创建、当前用户拥有、事件数 0；不是让模型创建旅程。
- **权限集**：owner、同行 member、未授权 stranger；提案始终属于 owner。失权用例在预览后变更 member 权限，或保护最后一项操作的事件。
- **关联影响旅程**：待移除事件有合成照片与账单；待改址 STAY 有合成酒店信息与供应商绑定；相邻交通有有效路线。真实附件内容不发模型，只传数量/布尔摘要。
- **地点数据**：固定 MCP 夹具由团队手写，含杭州/成都各两家同名分店、唯一 POI ID、GCJ02 坐标、无坐标、空列表及错误响应。所有仅供展示字段使用唯一标记 `DISPLAY_ONLY_<case>_<field>`。禁止将真实供应商响应录制进仓库。通过模拟许可提供的可留存字段，来源台账由适配器产生，不能由模型自己宣布授权。

R12 对话脚本：
1. “2026年11月15日杭州的行程，取消景点，午餐后直接打车去杭州东站。保留午餐照片、正文和车站备注。”
2. 等待 v1 后：“把午餐提前到11:30，其他保持刚才的调整。”
3. GET 校验后，测试操作者明确确认 v2，再调用 apply。生成阶段不自动应用。

用户模拟器只按预先写好的答复规则响应：缺日期回答固定日期；同名地点按可见城市/分店选择；候选失效重新辨认；无法留存门店时明确接受文字安排。不得把答案、隐藏 POI ID 或目标命令塞进后续 prompt。超出脚本的问题标记 `needs_review`，不由另一个模型任意补齐。原M诊断场景最多6次用户输入，全程E场景最多10次（包含首句、补充和答复）；超限算任务未完成，不能无限对话直到成功。E场景如何提供补充要求及注入环境变化，见用户全程案例。

## 判分器与不变量

**确定性判分优先。** 从预览和最终业务状态判定，不要求模型生成完全相同的 JSON 命令顺序、标题、draftRef 或随机 ID。为每个新增项按语义角色匹配真实 ID，检查引用指向同批此前创建且仍存在的事件；两项不能映射到同一 ID。删除交通和景点的合法顺序可不同，最终效果必须一致。约束文本和问题措辞可不同，但日期/分店歧义必须被明确解决。

所有 workflow 用例适用：

1. **预览隔离**：create/turn/question/cancel/discard 不改变正式事件、关联资产、投影、旅程修订。提案/运行表允许按生命周期变化。
2. **冻结确认**：apply 只收版本；确认版本、最新版、基准修订、权限均匹配才写。确认期间模型与 MCP 调用计数必须为 0。
3. **原子效果**：成功只新增一次修订；事件业务字段、顺序、关联影响与 committableDiff 一致。失败后正式事件、投影、修订、提案终态和回执均与 apply 前一致。
4. **恢复一致**：同键同参重放同一个 run；同键异参 409。成功 apply 重放返回原 appliedRevision；不把当前旅程的新修订冒充原回执。
5. **留存边界**：合成 DISPLAY_ONLY 标记不能进入数据库中的提案/版本/问题/约束/事件/修订或捕获的应用日志。检查所有嵌套字符串与数值/坐标对象，不只检查事件 title。测试报告仅记录泄漏字段路径，不复制原始值。
6. **约束**：hard=true 时只有 satisfied=true 才可应用；verificationRequired=true 且无证据也阻止应用。交通耗时未验证不能当成到站承诺。

R12 的额外判分：确认前仍 R12 五项；v2 相对 v1 仅 L 的时间相关字段变化；确认后 R13 且顺序 L/新交通/S，L/S ID、照片、正文、S 备注保留。新交通为 TAXI、EMPTY，端点 L/S，不得伪造 READY 路线。空旅程确认后三项不同 ID、站/交通/站顺序、合法端点，只增一次修订。

对于缺日期、分店歧义、要求固定不可留存门店的输入，正确终态可以是 `QUESTION`，而不是强行生成可应用版。对于外部故障，正确降级为不虚构地点的文字安排或清楚的问题；不能将供应商故障后的 HTTP 错误笼统计为模型逻辑失败。

## 执行与评分入口

正式模型用户任务集为 S 16例×3次 + E 12例×3表达×3次，共156个episode。先以6个单点和4个全程场景做冒烟；原M工具诊断、W系统回归和L真实接入独立报告，不混进全程任务成功率。

主指标为完整任务成功率及口语稳定性；分项包括硬约束满足、禁止项违反、编辑召回/精确率、保护信息保持、必要澄清与误问、行程质量及效率。错误写入、越权、留存泄漏和重复修订是独立硬门槛，不能由平均分抵消。公式、分母、未执行样本处理和质量评分标准统一见 [metrics.md](metrics.md)，避免多处定义不一致。

报告保留固定源码、数据版本、模型配置、case/variant/repetition和脱敏结果；真实凭据缺失记blocked。只保存判断所需事实，不保存完整真实工具输出、模型思考或凭据。当前为设计，未运行正式benchmark。

## 落地顺序与现有测试复用

1. 先实现S01/S03/S07/S08/S10/S14及E01/E06/E10/E12这组口语/全程冒烟，验证从用户输入到保存重开的真实Pi闭环；再扩展全部用户任务和三种表达。并行于此抽取测试夹具和上述状态判分，接现有 service/runtime 测试入口；先实现 W01/W02/W08/W17 的可重复执行与统一报告，再补矩阵。现有 `planning-service.test.ts` 已覆盖多个相同不变量，应复用，不复制另一套产品归约函数充当 oracle。
2. 用正常账号将 W01/W03/W08/W14/W16 接六个真实 HTTP 接口，核对与服务层同一结果。浏览器只补“展示版本→明确确认”、断响应恢复和冲突再确认三条关键交互，不把所有数据库用例重复成 UI 用例。
3. 接真实 Pi + 合成 MCP，跑 M01–M10；必须验证实际模型调用发生，不能让固定 runtime 绕过模型。最后跑 L01/L02 检查真实高德接入。

现有依据：`tests/unit/modules/planning/planning-service.test.ts`、`store.test.ts`、`ui.test.tsx`、`tests/unit/modules/agent/planning-runtime.test.ts`。当前这些是回归测试，不是已经形成的 benchmark 分数。当前真实模型凭据是否配置应在执行时检查；本次只交付设计和用例目录，未发起模型付费调用。
