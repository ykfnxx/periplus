# Periplus 旅行规划 Benchmark 设计稿

版本：1.0 · 2026-11-12 · 状态：设计待实施

实现基线：PR #70 `7c3fd2ab2d10e9b62848b6f671a663bfba0331c9`；工作分支：`feat/agent-plan`。本稿是独立设计文档，可不阅读此前讨论直接评审和实施。规范依据：[Pi 规划 workflow SPEC](https://app.raft.build/artifacts/5niAJkQrtr54F2Dq7UgBZU)。本次没有实现 runner、运行真实模型或产生 benchmark 分数。

## 1. 目标与边界

评估用户用日常语言提出旅行要求后，系统能否经过必要澄清、多轮规划与调整，给出符合要求的预览，并在明确确认后正确保存。比如“给我规划一个杭州三日游，不去灵隐寺”，测试应覆盖整段用户任务，而不只检查某个接口或生成 JSON。

同时回答四个问题：理解得对不对、规划是否满足要求、交互是否能顺利完成、正式数据有没有正确写入。工作流不变量、工具诊断和行程质量分别解释失败原因，不能互相替代。

本设计包含59个逻辑场景：19个工作流不变量、10个工具/模型诊断、2个真实服务接入、16个口语单点、12个全程任务。每个全程任务有3种等义首句，共36个初始表达。所有数量均为设计覆盖，不是已通过的测试数。

不评估自动订票、真实预订、支付或当前产品尚未提供的能力；输入涉及这些事项时评估正确说明边界和澄清，不要求虚构完成。地点服务的详情不能替代真实交通耗时或营业/票务证据。

## 2. 完整任务成功的定义

一次完整任务（episode）从首句用户输入开始，到用例指定的最终状态结束。成功是以下条件的合取，而非平均分：

`成功 = 用户目标满足 AND 过程正确 AND 最终状态正确 AND 无硬失败`

- 用户目标：对话中仍有效的明确要求全部满足；改口撤销的旧要求不再计分。硬约束未知不能按已满足处理。
- 过程：缺必要信息先澄清；预览不修改正式事件；取消、冲突、重试和版本确认按契约进行；不因用户选中地点就自动应用。
- 最终状态：普通任务确认后从数据库和重开页面都能读到与预览一致的结果，只增加一次修订。放弃任务的成功状态是提案关闭且无正式写入；取消一轮的任务应保留并明确确认原版。
- 硬失败：越权、未确认写入、数据泄漏、误改受保护资料、重复修订或事务部分提交，任意一次均使该episode失败。

判分器独立于被测模型。日期、时间、顺序、ID、修订、附件及保存一致性由代码断言；实际地点目标由引用、别名和语义标签判断。无法确定的语义由人工盲评，记待判，不能自动通过。模型说“已完成”、HTTP 200、合法 JSON 都不是充分条件。

“第三天16点到站”在用户允许保留未核实事项时可作为安排保存，并清楚标记交通未验证；若用户要求“必须确认能在16点前到”，无证据就不能判成功。两种输入必须分开标注。

## 3. 被测链路与隔离方式

```text
用例/普通用户会话
  → create / turns
  → Pi真实模型（或明确标注的固定runtime）
  → 地点工具与finish_turn
  → 领域预演、不可变版本、GET恢复
  → 用户确认指定版本 / cancel / discard / rebase
  → 数据库事务
  → 独立读取正式旅程与回执
  → 重开页面检查
  → 独立判分器与结果报告
```

| 执行层 | 依赖 | 可以得出的结论 |
| --- | --- | --- |
| workflow（W） | 固定模型输出、真实领域服务与独立PostgreSQL；正常登录会话驱动HTTP | 状态、权限、事务和恢复正确性，不代表模型能力 |
| model（S/E/M） | 真实Pi模型、合成且固定的MCP连接响应、真实适配器解析及领域服务 | 语言理解、工具使用、规划与多轮任务成功率 |
| live（L） | 真实Pi与真实高德MCP | 实际连接和跨城市调用能力，单列外部依赖故障 |

模型层不得用脚本直接插入成功版本。工作流HTTP层如需固定runtime，在测试服务装配点注入，不提供产品测试开关或公开测试路由。复用现有 `executePlanningRun`、`createPiPlanningRuntime` 等依赖边界，不能复制产品归约逻辑来制造同源“标准答案”。

所有层使用独立数据库和测试账号，不触碰实际旅程。使用者、同行与陌生人是不同正常会话；权限测试不依赖绕过认证。浏览器重点验证确认版本、重开、冲突和失响应恢复；不是每个数据库故障都重复做一次浏览器用例。

## 4. 数据、来源与对话驱动

固定测试时钟为2026-11-14T00:00:00Z，旅行时区Asia/Shanghai。首句允许缺日期、相对时间、指代和口语；绝对日期通过用户答复补齐。不能在模型没看到的隐藏夹具中填好日期，然后要求它猜中。

R12旅程：`L午餐 → T1交通 → G景点 → T2交通 → S杭州东站`。日期2026-11-15，L初始12:00并有两张合成照片与正文，S有需保留备注。T1连接L/G，T2连接G/S。真实落库ID按本次运行命名空间映射，评分比较逻辑角色。空旅程已由用户创建；关联影响夹具另外包含酒店、供应商绑定、账单和已解析路线。

地点数据手工合成，覆盖城市、同名分店、馆区、无坐标、空结果和故障；评分端另有别名与区域标签，不暴露给模型。仅供展示字段以唯一标记标识，扫描提案、版本、问题、约束、事件、修订及日志是否泄漏。不能把真实供应商响应录进夹具仓库。

用户模拟器按预写答复工作：缺日期等系统提问再答；节奏和范围等必须条件在日期确认后主动补充；候选只能根据当前可见内容选择，不能塞入隐藏POI ID。每条oracle依赖的要求必须真正进入对话。未知问题记needs_review，不能临时编答案帮模型过关。

E场景最多10次用户输入，M诊断最多6次；首句、补充、答复、调整均计数。到上限仍未到目标为失败。确认/取消/重试另记操作数。每个变体和重复均重建独立数据，不能共享上次回答或缓存。期望命令、评分条件不发送给模型。

### 4.1 夹具具体化

实现 runner 时按场景实例化以下最小数据，不使用真实用户数据：

- `dated-hangzhou`：已知日期2026-11-15起三天；`hangzhou-three-day-preview` 有三天已发布预览。
- `hangzhou-with-westlake-and-lingyin`：两个不同ID活动西湖、灵隐寺，日期固定；用于否定作用域。
- `preview-two-museums-day2`：第二天有两个不同馆；`preview-one-museum-day2` 只有一个，形成最小对照实验。
- `preview-day2-lunch-12-tea-15`：第二天12:00午餐、15:00下午茶；`dated-xiamen-two-day` 为11月15–16日，其他活动带不可丢失备注。
- `R12-two-turn-preview`：R12的取消景点/新增直达交通，以及午餐12:00改11:30两轮预览。
- 地点夹具除名称、城市、馆区、坐标，还给评分端维护语义ID/别名/区域标签；这些评分标签不发给模型。禁止景点判定基于实际活动目标及引用，而非整段回复字符串匹配。若文字方案无法自动确定，交盲评，不能直接算通过。

合成地点数据仅用于可重复行为判断，不证明真实营业时间、价格、交通或地图数据正确。地理合理性和实际工具连接在 live 层另报。

## 5. 主案例 E01：杭州三日游，不去灵隐寺

初始状态：普通账号已经拥有一个空旅程；正式事件为 0，基准修订记为 R0（实际数值不要求为零）。工具使用合成地点响应，模型真实运行；成功提案不得预置数据库。

| 阶段 | 用户或环境动作 | 必须观察到的结果 |
| --- | --- | --- |
| 首句 | “给我规划一个杭州三日游，不去灵隐寺” | 理解城市=杭州、时长=3天、排除=灵隐寺。缺绝对日期先询问；不能拿系统当天填充可应用日期。 |
| 澄清 | “2026年11月15日开始，玩到17日。” | 目标日期确定为15/16/17日，排除要求继续有效。 |
| 补充要求 | “每天10点后开始，一天最多两个景点；午饭都要有。具体店名不用存，保留文字安排就行。” | 生成包含三天活动及午餐的 v1；每日最多2个景点，活动不早于10点，不把即时供应商门店/坐标写入预览保存值。 |
| 第一次调整 | “第二天别太满，午饭定在11点半，灵隐寺仍然别排。” | v2 的第二天午餐为11:30；其余明确约束保留，不能为调整一天重建全部事件。 |
| 第二次调整 | “第三天16点要到杭州东站，交通时间没查清楚就标出来，别说保证来得及。” | 最终版有17日16:00车站安排，未核实交通可行性明确展示；未擅自声明已验证。若该要求无法在当前安排下满足，先澄清而不是冒充成功。 |
| 检查预览 | GET、页面差异与数据库快照对照 | 覆盖3天，无灵隐寺活动；所有已明确约束可逐条核对；正式事件仍为0。展示文字含“不去灵隐寺”本身不是违规。 |
| 确认 | 测试用户确认当前显示版本，再发送 apply | 仅一次修订，实际保存与预览一致；应用期间模型与地点工具调用数为0。 |
| 重开 | 关闭页面后重新进入旅程，重新 GET | 从数据库恢复同一事件顺序、日期和业务字段；不依赖内存中的提案列表冒充保存成功。 |

不规定唯一景点清单。满足约束的西湖/博物馆/城市漫步等方案均可；不能为了便于评分强迫输出某条“标准答案”。是否确实慢节奏、地理上是否绕路是独立质量项，不能拿“模型说轻松”当作已经满足。固定地点夹具可以提供人工定义的区域标签判断跨区往返；真实交通耗时只能用有证据的路线数据判断。

### 6.1 单点理解（16例）

| ID | 能力 | 用户原话 | 判定要求 |
| --- | --- | --- | --- |
| S01 | 缺少绝对日期 | 给我规划一个杭州三日游，不去灵隐寺 | 先询问出发日期；不能把当前日直接当出发日；保留杭州/3天/排除灵隐寺 |
| S02 | 否定约束 | 杭州玩三天，灵隐寺就别排了 | 不得新增灵隐寺活动或把去灵隐寺作为某日主安排；说明中提及“不去灵隐寺”不算违反 |
| S03 | 否定作用域 | 别把西湖删了，灵隐寺才是不去的那个 | 保留西湖，移除灵隐寺；不得因“别/删”邻近而删错对象 |
| S04 | 改口覆盖 | 刚才说三天说错了，改成两天，灵隐寺还是不去 | 两天替代三天；保留排除约束；不能残留第三天活动 |
| S05 | 软偏好 | 别太赶，上午晚点开始，喜欢逛吃 | 保留慢节奏/晚开始偏好；未给具体时刻不能声称用户要求10点；可提出明确可改建议 |
| S06 | 显式时间约束 | 每天10点之前别给我排活动 | 所有活动不早于10:00；交通早到与活动开始区别处理；约束未知不得当满足 |
| S07 | 模糊指代 | 把第二天那个馆挪到第一天下午，其他别动 | 询问具体哪个馆；不得按名称相似或数组第一个猜测 |
| S08 | 明确指代 | 把第二天唯一的博物馆挪到第一天下午，其他别动 | 只移动指定馆并更新必要日期时间；稳定ID不变；不得重建其他事件 |
| S09 | 时间更正 | 午饭不是12点，是11点半 | L改成11:30且startAt/时区一致；其余字段不变 |
| S10 | 部分撤销 | 算了，午饭时间改回去，取消景点这件事照旧 | 只撤回时间增量，保留取消景点和直达交通；不是整个提案清空 |
| S11 | 双重否定 | 不是不去西湖，是不要再给我排灵隐寺 | 西湖可保留，灵隐寺排除；不存在“两个都排除” |
| S12 | 禁止擅自承诺 | 查一下附近吃饭的地方，别替我订 | 只能查找/规划；不得声称预订成功或新增预订号 |
| S13 | 复合局部修改 | 把第二天午饭提前半小时，再把下午茶删了 | 午餐11:30，删除下午茶，其他内容/附件不变；两项都完成 |
| S14 | 相互冲突 | 我10点才到杭州东站，但第一项必须9点到西湖，而且必须从车站出发 | 指出时间冲突并澄清；不可发布满足全部硬约束的假计划 |
| S15 | 地点歧义 | 安排去省博，不是孤山那个馆 | 利用排除馆区信息检索/辨认；不能选回被排除馆区；缺信息时问而非猜 |
| S16 | 价格证据边界 | 两个人三天总共最多1000，住宿也算，别超了 | 提取人数/总预算/含住宿；无价格证据标未核实或澄清，不能把任意估价当已满足硬预算 |

### 6.2 全程任务（12例，每例3种首句）

每例首句任选一个变体，随后按规定补充和追问执行；正常任务最终都要确认与重开。各例的oracle检查最终语义效果，不要求唯一景点清单或逐字相同命令。

#### E01 · 杭州三日游排除景点

初始夹具：`empty`；环境变体：`normal`。

首句变体：
- 给我规划一个杭州三日游，不去灵隐寺
- 杭州玩三天，帮我排一下，灵隐寺就算了
- 想去杭州待三天，怎么安排？别给我排灵隐寺

用户补充/条件答复：
- 2026年11月15日开始，玩到17日。
- 每天10点后开始，一天最多两个景点；午饭都要有。
- 地点只能展示的话，具体店名不用存，保留我的文字安排就行。

后续输入：
1. 第二天别太满，午饭定在11点半，灵隐寺仍然别排。
2. 第三天16点要到杭州东站，交通时间没查清楚就标出来，别说保证来得及。

必须满足：
- 日期仅11月15–17日且每天有活动/午餐
- 无灵隐寺活动；所有活动>=10:00且每天最多2个景点
- 第二天午餐11:30；最终包含第三天16:00杭州东站安排
- 交通可行性未核实明确展示；不能捏造已验证保证
- v2/v3保留前轮约束，正式旅程确认前为空

### 6.3 环境变体的精确触发点

- normal：每轮预览完成后发送下一条输入，最后明确确认，再重开读取。
- expire-choice：问题已产生后跨过120秒，重开并尝试旧选项；只在重新辨认后继续。
- concurrent-edit：预览后由同行提交备注修改推进修订，旧版apply必须拒绝，再rebase和再次确认。
- lost-apply-response：事务已提交后才丢弃响应，重试必须绑定原确认版本。
- cancel-turn：第二轮已启动、尚未结束时触发cancel，再释放延迟结果；迟到结果不能覆盖首版。
- discard：明确触发放弃操作，再重开检查提案终态和正式旅程不变。

这些事件通过受控响应和同步点触发，不靠任意sleep碰运气。文字“取消”需由UI或测试用户执行取消动作，不能把模型回复当作接口已经取消。

## 7. Metrics 与实验设计

任务成功、质量和成本分别报告；安全与正确性为硬门槛，不折算成可互相抵消的加权分。

### 7.1 完整任务成功率（主指标）

每个 E 场景从首句开始，只有达到指定终点、全部可判定硬条件通过、且无安全失败才算成功：普通场景保存后重开一致；E11保存明确选择的保留版；E12正确放弃且不落库。

- 计划成功率 = 成功 episode / 计划 episode。blocked 和 needs_review 保留在分母，另列数量；这是本轮实际完成程度。
- 可执行成功率 = 成功 / (成功 + 产品或模型失败)。同时报告 blocked 和 needs_review，不能单独展示此数字掩盖未执行样本。
- 按场景宏平均：先对每个 E 用例的变体和重复取成功率，再对12个场景等权平均；不让某个多轮场景或大量改写主导成绩。
- 重复稳定性：同一场景×表达的3次结果列为0/3到3/3。口语稳健率 = 三个变体均3/3的场景数 / 12；另列每例最好/最差变体成功率差距。不同表达不要求得到相同旅游计划，只要求满足等义需求。

未发起真实模型调用的脚本运行不能进入该分子。真实供应商故障记 blocked/provider_unavailable；给定工具故障的预设测试若处理错误，则记产品/模型失败，而非基础设施阻塞。

### 7.2 需求与修改准确性

对每轮维护独立于模型的用户需求台账，记录约束来源的 turn、作用对象、hard/soft、当前有效或已撤回。用户改口后撤销旧约束，不把“三天改两天”按三天标准评分。台账只含用户真正说过的内容；模型自行新增偏好不能当作用户要求。

| 指标 | 定义 | 示例 |
| --- | --- | --- |
| 硬约束满足率 | 满足的有效硬约束 / 全部有效硬约束；unknown算未满足，单列数量 | 排除灵隐寺、3个当地日期、第二天午餐11:30 |
| 禁止项违反率 | 出现至少一项禁止安排的episode / 含禁止项episode | 实际排了灵隐寺，而不是文字提及“不去灵隐寺” |
| 请求编辑召回率 | 正确实现的请求效果 / 用户要求的效果 | “提前午餐并删除下午茶”必须两项都完成 |
| 编辑精确率 | 用户授权或领域必需的实际修改 / 全部实际修改 | 改午餐不应改车站备注；删除站点导致交通处理算必需连带修改 |
| 保护信息保持率 | 保留正确的受保护字段/关联 / 应保留字段/关联 | ID、照片、正文、账单关联、未修改的备注 |

修改按字段/顺序/关联的语义效果统计，不按命令条数统计。避免“一条命令更新20个无关字段”被计为一次正确编辑。无实际修改时精确率记 N/A，而非100%；请求召回仍判漏改。硬约束不满足但正确澄清时，单点 S 场景可成功；E 场景需完成答复后的最终目标才成功。

### 7.3 澄清和控制流

- 必要澄清召回率 = 在可应用版前正确提出的必要问题 / 夹具标定的必要问题。缺日期、指代不唯一、馆区歧义、不可兼得的时间要求属于正例。
- 无需澄清场景误问率 = 已具备必要信息却因无关/已回答问题阻断的单点数 / 无需澄清单点数。S07与S08作最小对照，避免通过“永远反问”拿高分。
- 重复追问率 = 已有效回答的问题被再次要求回答的次数 / 全部问题次数；候选真正过期后重新辨认不算重复错误。
- 对话状态保持率 = 后续轮次仍正确保留的有效约束 / 应保留约束。特别检查否定条件、日期、用户局部撤销以及 rebase 目标修订。
- 控制流正确性单列取消、放弃、重新预演、指定版本确认的通过情况；自然语言说“保存了”不等于调用成功。

问题是否必要由固定夹具标注；不明确的情况由人工看去标识记录裁决，保留理由，不以另一个模型的自由评分代替事实。

### 7.4 行程质量（次指标）

日期覆盖、事件顺序、时区一致、营业/交通证据的有无可以确定性检查。慢节奏、合理分区和安排实用性采用独立盲评，每维0–2分，报告分布而非并入安全总分：

- **节奏**：0明显违背明确时段/活动上限；1满足数字约束但拥挤或大量空缺且无解释；2满足约束且休息、活动衔接可理解。
- **空间组织**：0出现夹具可证的反复跨区绕行；1大体合理但个别重复；2按区域组织且解释必要跨区。不掌握真实路线时标 unknown，不能把直线距离当行车时间。
- **可使用性**：0缺关键日期/顺序，用户无法照着看；1大体能用但关键待核实项不清楚；2每日主活动和餐饮安排清楚，未知事实标明。

首轮由两位评审独立评分，记录分歧并复核；没有评审资源则该维度未评，不自动满分。不得因“推荐了预设名单之外的景点”直接扣分。模型 judge 如未来引入，需先与人工标注校准，本设计不依赖它。

### 7.5 系统不变量（硬门槛）

预览期间正式写入、越权读取/写入、泄漏即时地点数据、非原子应用、重复修订、保存结果与确认预览不一致：每项记录失败次数/检查机会以及受影响episode数。**任一出现即标记本版不满足正确性门槛**，即使任务成功率较高也不能抵消。

预览—保存一致率比较全部受影响业务字段、顺序和关联资料；回执重放同时检查原 appliedRevision 与当前 Journey revision，不能只看返回200。泄漏判分扫描提案/问题/约束/事件/修订/应用日志，不能只扫描最终行程。

### 7.6 效率与成本

分别记录成功和失败episode的用户输入轮数、必要澄清轮数、恢复操作数、模型响应数、高德业务调用数、首个可用预览耗时和完整任务耗时。用户等待的真实思考时间在自动脚本中不计入服务延迟；合成故障等待时间单列。

报告中位数、最大值及逐场景值；小样本不宣称可靠p95。token usage 来自供应商实际返回；缺失为null。货币成本仅在有明确模型价格版本时计算，不以猜测单价补齐。对比只在同一任务质量门槛下进行，不能因为模型提前失败调用少就评价更高效。

### 7.7 实验规模与比较

- 快速冒烟：S01/S03/S07/S08/S10/S14 + E01/E06/E10/E12，各1次；E仅使用第一表达。用于调试，不作为正式稳定性结论。
- 正式用户任务集：16个S各3次=48；12个E × 3表达 × 3重复=108，总156个模型episode。E的每个episode可以包含多次模型轮次，不称为156次API请求。
- 原有M01–M10用于工具/运行诊断，单独各3次，不混入E主指标；workflow和live仍分别报告。只在已配置并授权执行时运行，本次没有产生模型费用。
- 基线/候选使用同一数据、模型版本和配置，按场景与重复配对并交替执行以减小时间影响。先报告逐例差值与失败原因；置信区间如计算需按场景聚类，不能把同题改写当独立样本夸大置信度。
- 第一轮建立实测基线；未获得基线前不设想象中的“95%达标”。已有硬不变量仍必须零失败。

结果结构在原manifest上增加 `scenarioId, variantId, repetition, terminalGoal, activeConstraints, unmetConstraintIds, unexpectedEdits, missingEdits, preservedFields, clarificationLabels, hardFailures, qualityRatings`。原始真实工具结果和模型思考不入报告；保留脱敏判分事实和引用。单独展示设计覆盖与实际执行覆盖，59个设计场景绝不写成59个已通过测试。

## 8. Runner 交付方案

按三步实施，每一步交付可检查产物：

1. **固定输入与判分**：将本稿场景变为版本化夹具；实现语义ID映射、约束台账、业务快照比较、修订/回执检查和结果manifest。先用W01/W02/W08/W17验证判分器既能接受正确结果，也能拒绝删错事件、重复修订及部分写入。不得只测试“绿色路径”。
2. **真实模型冒烟**：S01/S03/S07/S08/S10/S14与E01/E06/E10/E12，从真实Pi模型到预览、确认、保存重开。确保模型调用确实发生、预览非预置；加入已知错误结果对照，证明约束/编辑判分能发现问题。
3. **完整基线与对比**：扩展全部口语/全程场景及三种表达，再跑真实杭州/成都接入。发布逐例结果、失败分类和费用/耗时；今后改prompt、模型或实现时固定其他变量做配对比较。

复用现有 `tests/unit/modules/planning/planning-service.test.ts`、`store.test.ts`、`ui.test.tsx` 和 `tests/unit/modules/agent/planning-runtime.test.ts` 的夹具及真实服务入口。现有回归通过记录不直接换算成benchmark成绩。

## 9. 实施验收

- 59个逻辑场景有固定输入、明确终点、版本化夹具及oracle；其中E场景具有实际发生的完整对话和环境变化。
- 每个报告可追溯到源码、模型配置、数据版本、场景/变体/重复；blocked与needs_review不可隐去。
- 主指标只来自真实模型完整episode；模拟输出与真实服务结果分别标识。
- 判分器经正反例校验，不根据模型自评、HTTP状态或答案关键词简单放行。
- 同一输入可在干净环境重复运行，结束后清理临时实例、登录和数据；真实工具数据不写入产物。
- 第一轮发布实际基线后再制定任务成功率改善目标；硬不变量始终要求零失败。

本稿交付的是设计。下一阶段的可观察完成标准是runner、实际基线结果和可定位的失败报告，而非再增加一份仅包含计划的文档。
